# Running

What a run does once the build has decided everything it can. Order, doors, failure, and the one lever a host keeps while a program is running. What is checked before any of this is [what an implementation checks, and when](CHECKING.md).

- A run starts from the declaration the host names when it starts the run, under *who may name a declaration* in [procedures](PROCEDURE.md). An image is every declaration the link judged, and which one runs is the host's choice each time. The host gives a value for every parameter the entry declares, null included where the parameter's type takes it, and nothing more: a parameter given nothing, or a value under a name the entry does not declare, **refuses at the run** before anything runs, and so does an entry taking a parameter in place, under *a parameter handed in place* in [procedures](PROCEDURE.md). What the entry returns the build held to the `returns` it declares, and it reaches the host as it is.
- Statements run in order; each binds its name in the scope of what follows.
- A call's arguments are evaluated in **position order**, the first first, whether the callee is a body, the host's or a value. An argument may call anything, so the order is observable: two arguments that would each refuse surface the one standing first.
- `Standard.Collection.keys` and `values` return in the dictionary's **key order**, under [the value model](VALUE.md), so a program that walks them gets the same walk on every run.
- A procedure's return value is held to its `returns`, `Null` where it writes none. A body and the declaration beside it are one document's text, so what the body reads is judged at the **build**: a reading the declaration does not take refuses there. Calling a value returns what the procedure type of the slot holding it writes after `->`, and that return value is held the same way. A reading the text opens to `Any` stands where *what a slot takes, exactly* in [types](TYPE.md) says a value read as `Any` does. Where a call reads a return value narrower than its callee declares (a type parameter the call filled, the return type a value's slot wrote, the return type a contract wrote for a row the run picks), the build held what the body returns to it, so the call reads what arrives as it is. What a value standing in a procedure-typed slot may return is held under *what a slot takes, exactly* in [types](TYPE.md). A call hands its return value on as it came, and the place it stands in reads it without remaking it. A variable the call hands in place is held the same way. A body cannot leak a value its declaration did not admit. What a native procedure hands back, and what it writes through a parameter handed in place, is a value from outside, as are the entry's arguments, what a host hands a closure, what a native procedure sends, and the failure a catch binds, whose `details` the failing procedure filled: each comes through a door, where every struct it holds, in a key as in a value, is fitted to the struct its name declares, under *a declared struct is nominal* in [types](TYPE.md), and the value is judged against its slot's type, and a value that does not fit, or that holds a `Double` with no finite value, which no document carries, **refuses at the run** there. A native procedure is called by the run and what it hands back comes back into it, so a value there that holds the type it was read as keeps that type, under *a value read as a contract holds the type it was read as* in [types](TYPE.md). The entry's arguments and a send are a call of the declaration they reach, so the door judges them the way the build judges a call's readings: what they read as once fitted fills the type parameters their slots name, and a parameter filled by two types, or a bounded one filled by what does not conform to its bounds, **refuses at the run**. Anywhere else a type parameter was filled by a call no value says, a send of a native procedure or the call that made a closure, so a value standing there is held to the bounds alone and taken at its host's word. A closure literal writes a signature and a body side by side too, and is held the same way where it is written.
- **A run can always be stopped from outside.** Cancellation is observed between statements and at the entry to every round, including a round with an empty body. This is the host's one lever over consumption, and it is the whole of the language's promise about time and memory: a program calling only the standard vocabulary can run forever, and nothing here predicts it. What is promised is that it can always be told to stop. Once told, a run raises no catch: a failure met after the cancellation reaches the host as it is, and no catch body runs.
- Leaving (`return`/`break`/`continue`) travels out through whatever it is inside, and is not a failure: no catch takes it. It does not cross a closure's edge: `return` inside a closure returns from the closure.

**A run refuses, and a refusal is not a failure.** Arithmetic past what an `Int` holds, a zero divisor under `dividedBy` or `remainder`, an index or a key that is not there read without `?`, a value arriving at a door that its slot does not take: each stops the run where it stands. No catch holds one, the way none holds a build's refusal, and it reaches the host as the run's refusal, saying where. A failure is what a procedure raised and a catch holds, under [statements](STATEMENT.md), and the two never trade places.

**Concurrency is isolation, and it is granted.** Warp's values are all data, so the only thing two bodies running at once could contend for is a written name, or a box a native procedure holds. What may run beside another body is an **isolated** closure, one that says it is and that the build holds to it, the way it holds constness:

- **Two kinds of body, told apart by where they are written.** Every `body` slot the document grammar has (a `conditional` arm, a `loop` round, a `try`'s body and its `catch`, an `unwrap`'s `then` and `else`) holds a body that runs here, in the flow that wrote it, and that is visible in the text, because no expression can carry one away. Such a body may `set` the enclosing variables. The one body that becomes a value is the **closure**: a *procedure*, with parameters and a declared return type, and a value may cross into a procedure, where no signature can say when, how often, or beside what the procedure runs it. So the split is carried by spelling rather than worked out by analysis: a body runs in place or is a closure by what it is written as, and the one channel into a procedure is the isolated one. A body that runs in place has no parameters, since nothing hands it anything, and a procedure has them.
- What a closure captures is the name as it is: a fixed name's **value**, and a variable's **box**. Making a closure runs nothing; a variable set between the making and the calling is seen by the call, because the box is one thing under one name everywhere it is visible. The closure's body is one of those places, so a closure may `set` a variable it captured; what it writes has to fit what the capturing body holds, held at the **build**, because the capturing body reads the variable as the type it gave it.
- **Isolation is declared, and a body is held to it.** A declaration or a closure literal says it is isolated by writing `isolated: true`. A body is isolated when it writes no name it did not declare (a module variable, or a variable a closure captured), hands none of those in place, calls a value only where the type written for it is an `isolated` procedure type, by the rule under *a const procedure* in [procedures](PROCEDURE.md), and calls only declarations that say they are isolated, and a body declared isolated that is not **refuses at the build**. The written type's mark is what says a called value writes only its own names, the same way a `const` procedure type is what says a called value is const, under *a const procedure* in [procedures](PROCEDURE.md), and a closure carries the mark for a name it captured. A closure value carries the constness, the isolation and the failures its signature declares, and a slot asking for any of them reads them wherever the value arrives, through a cast from `Any` included.
- **A native procedure says whether it is isolated, and is taken at its word for what it does itself.** The build reads what a body writes and calls; what a procedure keeps in the host language is outside the document, so the procedure declares it the way any declaration does. One that holds state between calls does not, and a body declared isolated may not reach it. `const` does not decide this: a procedure can be const and still return from a box two callers share. What the build does hold this claim to is what the procedure sends, under *a native procedure* in [procedures](PROCEDURE.md).
- **A procedure that runs closures at once asks for isolated ones.** `Standard.Concurrent.map` declares its closure an `isolated` procedure type, and `all`, `allKeyed`, `first` and `firstKeyed` declare their pieces a list or a dictionary of them, so a closure that writes a captured variable **refuses at the build** in every one. A piece returns a value; combining is written after the join, where the names are sequential again.
- Because a closure already says whether it is isolated, running closures at once is a thing a **procedure** can be handed (`Standard.Concurrent`, under the vocabulary), and so concurrency is a *grant*: a host that leaves the bundle out of the link has programs that cannot fan out at all.
- What this buys, exactly: **Warp itself writes no race.** Only isolated closures run beside each other, and an isolated closure has no writable name in common with anything, so no interleaving reaches a name two bodies hold. It is not "every result is deterministic": one thing is timing's, and it is named, which piece's value `first` returns. Everything else a join returns is the same under every interleaving. `all` waits for every piece, so a catch around a fan-out that lost twice is handed every failure, keyed by the piece it came from, whichever finished first. A piece that refuses at the run refuses the whole run, whichever finished first among the pieces the join waits for, and no catch holds it: a refusal is not a failure, and the failures beside it are not reported. `first` waits for no piece once one has succeeded or refused, under [vocabulary](VOCABULARY.md).
- **Effects are the world's, and the world is the host's.** Two pieces' host calls interleave in an order nothing states. Two pieces reaching one host-held thing, a file or a counter, is contention the *host's* procedure must defend. What the language guarantees is that a procedure holding such a thing declares it and the build refuses to run two of its callers at once. A procedure that holds state and declares itself isolated has broken its contract: the language takes a procedure at its word here, as it does for what one returns at a type parameter.
- **What the host holds lives where the host keeps it.** A file, a connection or a transaction is the host's: a value names it and says nothing about how long it lives, which the host's procedures say. Whatever is still open when the run is over, by a return, a failure, a refusal or a stop, is the host's to end. A value naming what the host has ended is a value like any other, and a procedure handed one fails as it declares, or refuses.
